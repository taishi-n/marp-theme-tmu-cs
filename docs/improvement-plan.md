# 利用セッションに基づくテーマ改善計画

調査日: 2026-11-05
実装の確認基準: `ac738fab72c06fc81cea592a7d937e9af2990a4b`

採否を個別に指定するための[番号付き項目一覧](improvement-items.md)を用意した．
解決先は[テーマ機能，作成スキル，個別repoの責務分担](improvement-ownership.md)に従う．
2026-11-05に対応が承認された．33は引用表示の3モード，37はテーマによる章扉の切り替えへ更新した．
段階ごとの実装と検証は[実施状況](implementation-status.md)に記録する．

このrepoでは，文献一覧の生成制御，比較図と音声の共通レイアウト，下部メッセージ，編集IDと索引を機能として扱う．
用途別の作成例と共通の執筆規約は作成スキルへ，研究固有の内容と数値は個別repoへ分ける．
wavegramの描画制御は当日の実装を再利用し，公開依存で再現できる状態を整える．

## 調査対象と数え方

ローカルに記録された他の親セッション60件のメタデータと，取得できた利用者の依頼文を検索した．
スライド関連語を含む15セッションから，実際にこのテーマを利用した8セッションを確認した．
利用側のMakefile，CSS，HTML後処理も読み，現在のテーマ実装と照合した．
依頼文を取得できない古いセッションもあり，全利用履歴を網羅した調査ではない．

この8件から代表的な依頼57件を抜粋し，検証範囲に関する補助セッションS9の1件を加えた．
[根拠資料](improvement-evidence.json)に，セッション識別子，利用者メッセージ識別子，日時，要約，分類を記録した．
会話の原文，添付資料，生成メディアは収録していない．

集計には利用者自身の依頼だけを使い，サブエージェントの指示，要約，自動監視の通知，履歴間の重複を除いた．
別セッションへ貼り直された同じ修正一覧も頻度の根拠に加えていない．
1件の依頼が複数の分類に属することはある．
以下の件数は抜粋で確認できた下限であり，依頼総数のランキングではない．
同じ資料を継続編集したセッションがあるため，横断性はリポジトリ数も併記して判断する．

## 実装順序と完了条件

各段階は個別にレビューできる変更へ分ける．
以下は採用前に整理した段階案である．
実装した設定とファイルの現状は[実施状況](implementation-status.md)と各機能ガイドを参照する．

### 第1段階: 作成スキルの例と作業規約

**優先度P0．対象は`tmu-cs-lecture-slides`スキルと，その参照資料や作成例である．**
根拠はR1，R2，R3，R5，R6，R7，R11であり，最も広く反復した指示へ小さい変更で対応できる．

| 作業 | 内容 | 完了条件 |
| --- | --- | --- |
| 用途別の例 | 長い講義，短い研究発表，実験報告の3例を作る | 各例に章扉，引用，本編と補足，ノートの扱いを明示する |
| 執筆規約 | 本文を短くし，詳細をノートへ移す．図と数式には理解に必要な短い説明を添える | 作成者がスキルから共通規約と作成例を辿れる |
| 結果ページ | 条件と意図を説明した後に，結果図と根拠のある短い結論を置く | 説明ページと結果ページの両方の例がある |
| 音声比較 | 既存の`data-wavegram-*`で波形，操作部，時刻の表示を選ぶ．magmaと同じ解析条件で複数チャネルを並べる | 設定を生成後に書き換えるJSなしで比較例をビルドできる |
| ビルドと確認 | 通常のHTMLビルドと静的検証，利用者の目視確認を別々の結果として扱う | 標準手順がブラウザを自動操作せず，未実施の目視確認を完了扱いしない |
| 検証範囲 | 文章と装飾の編集は差分，ビルド，必要な静的確認で扱う | 旧表現の禁止や特定ページの文章を固定するテストを追加しない |

執筆上の選択は例と規約で伝え，文章を自動変換する処理は設けない．
行列の書体や引用数は資料ごとに異なる依頼があったため，テーマ全体の固定規則にはせず，各デッキの規約を選べる形にする．
章扉も，長い講義では使い，短い発表では省き，必要な2か所だけ挿入する使い方を示す．
下部メッセージは2026-11-04の横断的な指定に合わせ，主に実験結果の図表へ使う．

### 第1段階の並行作業: wavegramの公開依存への統合

**優先度P0．対象は依存宣言，ロック，開発ガイド，配布パッケージの確認である．**
R8とR10への対応として，当日の描画制御を含むwavegramの公開版を確認し，必要な最低バージョンを揃える．
ローカルリンクを使わない一時的な利用プロジェクトで，テーマの配布物から比較例をビルドする．
現在の変更をもう一度実装する必要はない．

完了条件は，公開依存だけで必要なAPIが揃い，ローカルと配布物の両方が同じ設定を出力することである．
公開バージョンの確認が先行条件になるため，ドキュメント整備は独立して進める．
既存の`media-enhancements`，`spectrogram-visibility`，`media-playback`のテストを使う．
体感速度の確認は，利用者が多チャネルの実デッキを表示して行う．

### 第2段階: 引用と文献一覧の制御

**優先度P1．対象は`src/features/citations/`と文献ガイドである．**
R4に対応し，`citationDisplay: footnotes | bibliography | both`で引用表示を制御する．
既定値の`both`は現在の両方表示を保つ．通常のMarkdown脚注はこの切り替えの対象に含めない．
`bibliography:`は引き続き入力文献ファイルを表す．

短い脚注を使う手順とCSLの例は，作成スキル側で扱う．
脚注と文献一覧へ異なるCSLを独立指定する必要が生じた場合は，別の機能要件として検討する．
元のBibTeXからタイトルを削ったり，生成済みHTMLから文字列を切り取ったりする方式は採らない．

完了条件は，利用側が文献一覧のSVGラッパーを削除しなくても同じ意図の出力を得られることである．
現在の`onolab-research-intro`の後処理には，一覧を消すときにMarpの共有scriptとstyleを退避する処理がある．
この処理を不要にすると，資料構成の変更が表示機構を壊す危険を減らせる．
既存の引用とMarkdown脚注の共有番号，文献リンク，既定のIEEE出力を保つ契約を検証する．

### 第2段階: 編集IDとページ索引

**優先度P1．対象は`src/pipeline/slide-metadata.mjs`と関連するパーサーである．**
R9と利用側2リポジトリの索引生成を根拠に，編集IDと元のMarkdown行を生成ページへ対応づける．

提案する入力は，ページの固定IDを表す`<!-- slide-id: result-example -->`である．
エンジンは固定ID，元のMarkdown行，物理ページ，本編番号，補助ページ区分，生成ステップの索引を出力する．
編集用ラベルの表示は任意とし，配布用HTMLと印刷では既定で隠す．
タイトルや章扉の自動生成，コードのステップ展開も索引へ反映する．
固定IDは既存の見出しIDと目次リンクを変更しない．

付録の番号非表示と合計からの除外は，既存の`paginate: skip`を使うスキルの手順として扱う．
付録区分を索引へ出す機能が必要になった場合も，番号制御と分けて要件を決める．

完了条件は，ラベルと索引の生成を利用側のHTML後処理から外せることである．
重複IDの検出，並べ替え後のID保持，自動生成ページの対応，既存の番号制御との整合を検証する．

### 第2段階: 追加CSSの正式な適用経路

**優先度P1．対象はCLIラッパー，公開エントリーポイントの利用例，ビルド例である．**
R2と利用側3リポジトリのCSS結合処理を根拠に，ベーステーマへ追加CSSを適用する手順を共通化する．
まず現在のMarp CLIで実現できる範囲を確認し，不足する部分だけラッパーへ追加する．
新しいオプション名は既存CLIとの衝突を確認してから確定する．

完了条件は，作成者が`slide.css`だけを編集し，テーマ名の置換や`src/`への直接依存を持たずにビルドできることである．
公開パッケージのインストール先や作業ディレクトリが変わっても同じ結果を生成する．
既存の`--theme-set`と`--engine`による明示的な上書きは保持する．

### 第3段階: 図と音声の比較レイアウト

**優先度P2．対象は`theme/tmu-cs.css`と比較用のサンプルである．**
R2，R5，R6に対応し，結果図，短い結論，音声チャネルの行を配置する任意のクラスを用意する．
基本テーマの既定配置は保ち，利用側が必要なページだけに適用する．

図の表示領域と結論の領域をCSS変数で定義し，ページを送っても比較対象が動かない例を作る．
TikZやSVGの作成例では，キャンバス，図中の文字サイズ，色，余白を揃える．
軸の範囲，凡例，チャネルの順序，共通ゲインは図や音声の作成側で管理する．
テーマには研究固有の用語変換や音声の正規化処理を持たせない．

音声の行は短いラベル，ダウンロード操作，スペクトログラムの位置を固定する．
第1段階で示した既存属性を使い，読み込み後の属性変更を減らす．
完了条件は，複数の結果ページと多チャネルの例を，同じ図領域と文字サイズで生成できることである．
文字の折り返しや重なりの最終確認は，生成物を利用者が表示して行う．

### 第3段階: 共通の静的検証

**優先度P2．対象は検証スクリプトと利用例である．**
R7とR11に対応し，編集IDの重複，索引との不一致，未解決の引用，参照するローカル資産，数式エラーを静的に報告する入口を作る．
第2段階のメタデータを利用し，利用側で同じHTML解析を繰り返す量を減らす．

完了条件は，ブラウザを起動せず，ページIDとソース位置を添えた機械可読の診断を出せることである．
意味の適切さ，図の比較軸の妥当性，文字の見切れ，目視品質は別の確認項目として報告する．
研究固有の数値や出典ハッシュの検証は利用リポジトリに残す．

## 移行と検証の単位

作成スキルの文書と例，このrepoの依存更新，第2段階の各機能，第3段階の各機能を別々の変更として扱う．
各機能の移行は利用デッキ1件で先に試し，同じ役割の後処理を取り除けることを確認してから他へ広げる．
この計画だけを根拠に利用側のリポジトリを変更することはせず，採用する機能の実装時に移行範囲を決める．

| 変更 | 主な確認 |
| --- | --- |
| 文書と執筆規約 | 差分，リンク，属性名と既存仕様の照合 |
| サンプルとCSS | HTMLビルド，構造と資産の静的確認，利用者の目視確認 |
| 引用，パーサー，ページ番号 | 継続する公開契約を検証するテスト，HTMLビルド |
| standaloneとCLI | 既存テスト，決定的なstandaloneビルド，必要な配布物確認 |
| PDFに影響する構造変更 | 必要なPDFビルド，本編数と付録区分の確認 |
| wavegramの依存更新 | 既存メディアテスト，ローカルリンクなしの利用例ビルド |

承認後は，引用と章扉，共通レイアウト，編集メタデータとCLI，スキル，利用側への移行を分けて実装した．
公開依存の確認はwavegramの公開許可と認証後に完了した．
実施結果と検証範囲は[実施状況](implementation-status.md)に記録した．
